# Book glossary synchronization v1

`GET /api/v1/book-glossary?providerId=...&bookId=...&targetLanguage=...` and `PUT /api/v1/book-glossary` synchronize one complete ordered glossary snapshot for the authenticated account. The key is the exact original provider/book pair and a concrete lowercase target language, independent of local document UUIDs, display title and translation fingerprints. GET query keys must appear exactly once; unknown keys are rejected.

Prefer `POST /api/v1/book-glossary/query` with strict JSON `{providerId,bookId,targetLanguage}` for reads. It has the same read-only behavior as GET, requires authentication and CSRF, and consumes no write quota. A 16 KiB request-body limit covers maximum original IDs without percent-encoded URLs exceeding HTTP request-line limits. GET remains available for shorter IDs.

PUT requires `{providerId,bookId,targetLanguage,expectedVersion,mutationId,entries}`. The response is `{providerId,bookId,targetLanguage,version,entries,updatedAt}`. An absent GET returns version `0`, entries `null`, updatedAt `null` without creating a row. `entries:null` writes a versioned tombstone; `entries:[]` is a present empty glossary. A successful write increments the version once. An exact replay of the latest mutation returns the same version and timestamp; reusing that mutation UUID with other contents gives `400 BOOK_GLOSSARY_MUTATION_REUSED`. An older expectedVersion gives `409 BOOK_GLOSSARY_CONFLICT` and the exact current view. The safe-integer version ceiling gives `409 BOOK_GLOSSARY_EXHAUSTED` without current.

Every entry includes all fields: `{id,sourceTerm,translatedTerm,displayTerm,kind,caseSensitive,enabled}`. `kind` is `Character`, `Place` or `Term`. The snapshot retains entry order, original opaque IDs, disabled rows and every display attribute. Duplicate source terms are valid; duplicate entry IDs are not. No deduplication, normalization, truncation or merge happens on the server.

All limits count UTF-16 code units: providerId 1–100, bookId 1–2000, entry id 1–200. Identity values reject boundary ECMAScript whitespace, ISO controls and unpaired surrogates rather than changing their value. sourceTerm and translatedTerm are 1–200 and nonblank after ECMAScript trim; displayTerm is 0–200. Entry text preserves outer whitespace, rejecting only controls and malformed Unicode. targetLanguage has 2–24 characters matching `[a-z]{2,8}(?:-[a-z0-9]{1,8})*`, excluding `auto`; inputs are never silently lowercased. At most 500 entries fit one snapshot; the entire UTF-8 JSON request must additionally fit 1 MiB. Clients may bound responses at 2 MiB.

Requests use authenticated same-origin transport and CSRF for PUT. Strict JSON rejects extra/missing/duplicate fields, trailing values, numeric or boolean coercion. Responses have `Cache-Control: no-store`. There are at most 120 PUT requests per account per minute (including exact replays); `429 BOOK_GLOSSARY_LIMIT` includes Retry-After. Oversized bodies, including chunked requests, fail with 413 before JSON binding. GET and writes never fetch source sites. Account deletion removes snapshots. A storage-only SHA-256 index avoids PostgreSQL btree limits for long original IDs; every lookup also compares the full original identity, and the public identity remains unchanged. A transaction advisory lock over an unambiguous account/provider/book/language tuple serializes compare-and-set writes.

Clients explicitly adopt or replace a local glossary and keep local data until that choice. They persist outbox mutations before transmission, replay unchanged on lost responses, keep newer edits separately while a write is in flight, and compare the actual displayed local/server snapshots before resolving conflicts. Merely viewing a book never uploads or deletes its local glossary. A sync `version` is independent of `translationFingerprint`: changing displayTerm or kind must synchronize while retaining translation cache identity.

The workflow and reading-translation APIs accept an optional exact entry `id`. Omission retains the legacy source-hash ID, trim/default omission and source sorting. Explicit IDs retain their fields and order and feed the existing runtime fingerprint. Effective IDs must be unique even across explicit and legacy entries. A group of duplicate normalized source terms is valid only if every member has an explicit unique ID; legacy or mixed duplicate groups are rejected. Workflow requests still have a 200-entry limit: clients project enabled entries from the full snapshot, explicitly reject an oversized projection, and keep all inactive entries in the account snapshot.
